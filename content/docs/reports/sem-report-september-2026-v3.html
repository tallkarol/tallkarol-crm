01

What this re-run found

Version two reported that August traffic had fallen sharply and that Google Analytics had recorded nothing yet for 1–2 September. It read those as a traffic problem and a reporting lag. Both readings were wrong, and this run can prove it.

Analytics stopped measuring most of the site on 17 July, the day a cookie consent banner shipped. Since then Google Analytics has only ever seen the visitors who click “accept” — roughly one in twelve. Every number in the v1 and v2 reports drawn from Analytics after 17 July is a sample of about eight per cent of reality, not a measurement of it. August did not lose ninety per cent of its traffic. It lost ninety per cent of its measurement.

On top of that, Analytics has recorded nothing whatsoever since 1 September, while the site has continued to serve real visitors throughout. Both faults have now been traced to a single cause in the Tag Manager container, confirmed in a real browser against the live site — section 02 sets out the evidence.

The one-line version

The advertising account is now built correctly and is spending on the right searches. The measurement underneath it has been broken since mid-July and completely dark since 1 September, so nothing the campaign does can currently be judged. Fixing measurement comes before every other decision in this report.

Vercel Analytics was switched on 31 August, which is why the comparison starts there. Before that date there was no independent counter to catch the problem — which is precisely why it went unnoticed for six weeks.

This is not a reporting delay

Google Analytics can take up to two days to finish processing, so an empty yesterday proves nothing on its own. The Zemvelo property settles it. It sits in the same Analytics account, is read by the same service account, on the same standard (unpaid) service tier:

176Zemvelo users, 2 SeptAlready processed and reported

0Mineralife, 2–3 Sept & liveNo rows at all, realtime empty

Processing is current. Mineralife’s property is not being sent anything.

What is verified working

  • The Tag Manager snippet is on the page — container GTM-5B83HMG loads.
  • The container holds the correct measurement ID, G-VM816RCN4R, in eight places.
  • The Analytics data stream and the Google Ads link both exist and are configured.
  • The consent banner component is still rendered on every non-admin route in the code.

So the fault is not a missing tag or a wrong ID. It is that the tag never receives permission to fire. Consent defaults to analytics_storage: 'denied', and Analytics only starts recording once a visitor presses accept.

The cause, confirmed in a browser

The live homepage was loaded in a real headless Chrome, with a clean profile, and driven the way a first-time visitor would drive it. The banner is not the problem. It renders correctly, sits in the viewport, and both buttons pass a hit test with nothing overlaying them. Pressing Accept works exactly as designed: the choice is stored, and analytics_storage: 'granted' is pushed into the data layer.

And then nothing happens. With consent granted, the page was watched for a further twelve seconds:

0Requests to Google AnalyticsAcross the whole page load
0Cookies setNo _ga, none at all
1Third-party request in totalThe container itself, nothing more

Reading the published container explains why. It holds eleven tags. The Google Analytics configuration tag — the one that must run before any measurement can happen — has exactly one trigger: Initialization, and it carries a required consent check on analytics_storage.

The defect, in one sentence

Initialization fires once, at the very start of the page, when consent is still denied by default — so the configuration tag is skipped, and because Initialization never fires again, pressing Accept a few seconds later can no longer bring it back. A visitor who accepts cookies is still never measured.

That also explains the eight per cent. The site reads a previously stored choice and grants consent before the container loads, so a returning visitor who accepted on an earlier visit does have consent in place by the time Initialization runs, and is counted. Everybody arriving for the first time is invisible no matter what they click — which is most of the traffic, and all of the traffic the advertising pays for.

The fix

In Tag Manager, give the Google Analytics configuration tag the All Pages trigger instead of Initialization, or add consent-update as an additional trigger. It is a container change and a republish — no site deploy is involved. Everything downstream of it, including the seven event tags for form_submit, generate_lead and the rest, is already correct and waiting.

A second, smaller defect found in the same pass

The site’s Content Security Policy allows googletagmanager.com for scripts and connections but not for images, so Tag Manager’s own image requests are being blocked and the browser console logs a policy violation on every page load. It is not what is stopping measurement, but it should be cleared up: add https://www.googletagmanager.com to the img-src list.

A correction to this report’s own first draft. Before the browser check was run, this section proposed that the 1–2 September hero rebuild had covered or broken the consent banner. That was wrong. The banner is intact, the deploys are not implicated, and the fault predates them — it is in the container.

Impressions fell by about ninety-five per cent and the cost per click went up twenty-five fold. That reads like the campaign broke. It did not. Look at what the cheap clicks were.

Through 1 September a single broad-match keyword, nutra labs, produced 92 impressions and 20 clicks for $1.67. The searches behind those clicks were things like nutrition manufacturing companies (3 clicks, $0.08), food supplements manufacturers (3 clicks, $0.07), supplement manufacturers (2 clicks, $0.05) and nutraceuticals (1 click, $0.02). Clicks at two to eight cents with a twenty-to-thirty per cent click-through rate are not buyers on Google Search. Analytics confirms the source: sessions arriving from syndicatedsearch.goog — Google’s search partner network, not Google itself.

So the collapse is the fix working

Turning off the search partner network and moving broad match to phrase match removed almost all the volume, because almost all the volume was worthless. The account now buys a handful of expensive, relevant clicks instead of hundreds of cheap, irrelevant ones. That is the right trade — but it does mean every historical click, cost-per-click and click-through figure for Competitors is not comparable to anything from 2 September onward.

A question that needs an answer: the Performance Max campaign

The shared Ads account also runs 2023 — Performance Max — Maximize. Between 28 August and 3 September it spent $82.35 — more than the two B2B search campaigns spent together ($55.33) over the same week. Because the reporting splits this account by campaign name, and that campaign has no “B2B” in its name, every cent of it is currently attributed to Zemvelo and none of it appears in Mineralife’s figures.

If that campaign is in fact Mineralife’s, real Mineralife spend is roughly double what is being reported, and the $600 budget is already being exceeded substantially. If it is Zemvelo’s, the reporting is correct and no action is needed. Somebody needs to confirm which. It is the only open question in this report that could change the numbers by a factor of two.

Two of these came from paid search, both from the Competitors campaign. So the goal stated in version two — the first attributable US enquiry — was in fact reached twice in August. Google Ads simply never counted it, so no bidding decision has ever been able to use it.

The plumbing explains why. generate_lead was only marked as a key event in Analytics on 30 August, after both enquiries had already happened, and Analytics does not apply that designation retrospectively. catalog_download was marked on 1 September. The Google Ads link exists and was last touched on 1 September, but no conversion from it is being counted in Ads.

Two smaller things in the same table

Two of the nine enquiries came from localhost:3000 — a developer machine filing test leads into the production Analytics property and into the lead records. Those need excluding, and the internal-traffic cookie the site already supports is the mechanism for it.

Every figure in this report was read from the live systems on 3 September 2026, not from a cached report or a previous version. Specifically:

  • Index scan — URL Inspection API against Search Console property sc-domain:mycustommanufacturer.com, 63 sitemap URLs, run 3 September.
  • Advertising — Google Ads API v25, account 624-370-2566, campaign, keyword and search-term reports queried per day for 28 August to 3 September.
  • Analytics — Analytics Data API against property 395780153, daily and realtime, cross-checked against properties 305233533 (Zemvelo), 498136327 and 551968841 to rule out processing delay.
  • Search Console — Search Analytics API, queries and pages, compared fortnight by fortnight from 7 July.
  • Site — live HTTP checks of the homepage, redirects and canonical tags; the Tag Manager container GTM-5B83HMG downloaded and inspected; deploy history and source history read directly from the site repository.
  • Speed and uptime — PageSpeed Insights, live mobile and desktop audits; UptimeRobot monitor 803863309.

The measurement fault in section 02 was confirmed by driving the live homepage in a real headless Chrome with a clean profile: the consent banner was located and hit-tested, Accept was clicked, and every network request and cookie was captured for twelve seconds afterwards. The published Tag Manager container was then downloaded and its tag, trigger and consent tables read directly. Nothing in that section rests on inference.
