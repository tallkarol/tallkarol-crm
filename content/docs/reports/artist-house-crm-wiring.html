TALLKAROL CRM · proposal, part three

The daily run failed twice. Nothing told you.

Artist House already records every ingest run, every sign-in, every access request — and it already has a support form that emails you. None of it reaches the CRM, so a two-day outage is something you find out by looking. This wires the app's own record into the ticket queue, turns silent failures into tickets that escalate, and puts feature requests where you can quote them.

01 — the inventory

What already exists

Read off the repos, not assumed. Most of this proposal is plumbing between things that are already built — which is why it's small.

artist-house · server

Runs are already recorded

  • ingestion_runs — kind, trigger, started/finished, ok, status, jobs total / succeeded / failed / skipped, api_calls, stats, and an error jsonb
  • ingestion_run_jobs — per-job detail under each run
  • cron_daily_coordinator — status, phase, holder, heartbeat_at, last_error, plus a staleness window (default 600s)
  • GitHub Actions — 11:30 UTC → POST /internal/cron/daily-ingest, then polls status for up to 6h

artist-house · front-end

A support form that emails you

  • /support-tickets — category (bug / question / feedback / other), subject, message, reply-to, page URL, up to 3 screenshots ≤1MB
  • send-ticket-email.ts — sends to hello@tallkarol.com, with submitter name, account email and role attached
  • rate-limit.ts — per-user throttle already in place
  • app_user (role, last_login_at), login_failure, app_user_request, email_send_log

tallkarol crm

A queue with an open door

  • POST /api/support/ingest — bearer auth, client by slug, tags, env, and labelled code payloads
  • support_tickets + ticket_messages + ticket_payloads
  • /logs and /uptime — routed, in the nav, and still empty placeholders
  • clients · projects · proposals · timesheet · invoices — everything a ticket would need to become money

So the gap is narrow. Artist House knows a run failed; the CRM knows how to hold a ticket; nothing carries one to the other. And the one failure neither side can see today is the run that never starts — no error is thrown, no email is sent, and the coordinator simply keeps yesterday's row.

07 — the stream

Which events are worth keeping

Not logs. Railway keeps logs. This is the short list of things you'd want on a timeline six months from now, when a client asks what happened.

EventKept becauseVolume
auth.signed_inWho actually uses the thing you bill for — the strongest renewal argument you have~10/day

Retention: 90 days raw, then daily rollups kept indefinitely — sign-ins per week per client is a number worth having a year later; the individual rows aren't. At these volumes the whole table is a few thousand rows a month.

08 — sequencing

Four increments

1

Reroute the widget

  • app_sources table + per-app key, issued from CRM settings
  • Artist House posts to /api/support/ingest, email as fallback
  • kind on tickets; category maps to lane
  • Console errors and app version ride along as payloads

Smallest piece, endpoint already live. Value on day one.

2

Runs and monitors

  • monitors + monitor_runs in the CRM
  • Three calls around the existing cron coordinator
  • Incident rules: open, append, escalate, resolve
  • Sweeper for missed windows — the failure nothing catches today
  • /uptime becomes the monitors screen
  • One-time backfill of ingestion_runs so history isn't empty

This is the piece that would have caught this week.

3

The activity stream

  • app_events + the short event list
  • /logs using the filter bar and bands already built
  • Rollups and 90-day retention
  • Per-client health strip: monitors, open tickets, hours this month

Useful, not urgent. Nothing depends on it.

4

Ticket to money

  • ticket_id on time entries; log time from the ticket
  • Request → estimate → deliverable, carrying the ticket with it
  • Billable flag and per-client roll-up
  • Optional: status back into Artist House so they can see their own tickets

Depends on where the punch clock work lands.

Where do screenshots live?

Three 1MB images per ticket is nothing at your volume, so bytea in Postgres with an authed CRM route is the simplest thing that works and needs no new service. It does put binaries in the database you back up. The alternative is object storage and a signed URL — more moving parts for a feature that fires a few times a month. I'd start with bytea and a 3MB cap per ticket.

What runs the sweeper?

A missed window needs something on a clock inside the CRM. Railway cron on the CRM service is the obvious answer, but you already use GitHub Actions for the Artist House daily — reusing that pattern means one place for schedules and one place they can silently stop. Whichever you pick, the sweeper should also monitor itself: if it hasn't run in an hour, the dashboard says so.

Does the recovery close the ticket?

A run that succeeds after two failures usually means you fixed something worth billing, so auto-closing hides the work. My default: post the recovery, drop priority to normal, leave it open, and let closing be the moment you've logged the hours. It's a per-monitor setting either way.
