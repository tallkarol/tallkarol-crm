TALLKAROL · internal infrastructure · proposal

Always-On Worker

Everything that can run in the cloud, runs in the cloud. One always-on laptop at home does the three things the cloud cannot: run Claude Code on the subscription, drive a real logged-in browser, and use a GPU. The CRM never learns the laptop exists — it only knows about jobs.

01 — the read

Where it breaks

The CRM's AI surface is smaller than it feels. There is exactly one Anthropic call in the whole app — the notebook scan in lib/notion-scan.ts — and it bills to an API key. Everything else that looks like AI in this practice is Claude Code itself, run by hand from a terminal on a Mac that sleeps when the lid closes. The two problems are separate and want different fixes.

1API call sitenotion-scan, zod structured output. The only thing paying per token.
0sanctioned waysto put Pro/Max credentials inside the CRM or the Agent SDK. Policy since Feb 2026, enforced since Apr 2026.
0always-on machinestoday. Puppets, snapshots and Lighthouse runs only happen while the Mac is open.
8 / 16GB VRAM, unconfirmedThe 3080 laptop part shipped both ways. Decides the optional local-inference tier, nothing else.

The subscription cannot be borrowed

Anthropic restricts consumer OAuth to Claude Code and claude.ai. The Agent SDK quickstart says to use API keys; --bare headless mode does not even read the long-lived token. A personal internal tool is not an exception. What is sanctioned is the Claude Code binary itself running non-interactively on a machine you own, with a token from claude setup-token — the documented CI path.

Puppets need a body

Lighthouse against prod, docent screenshots, the leftoff Chrome tab snapshot, headless CDP verification — all of it needs a real Chrome, often a logged-in one, on a machine that is awake. Railway cannot open a browser and Anthropic's cloud routines cannot reach your sessions. The Mac does both, but only when you are sitting at it.

So the direction flips. Instead of the CRM calling Claude, Claude Code and a small worker call the CRM. The app enqueues; a machine you own dequeues. The subscription is spent by Claude Code, the puppets get a body, and the API key stays as the fallback for the day the body is switched off.

02 — the split

Cloud first, laptop for what the cloud cannot do

One rule decides where a thing runs: if a cloud routine or the Railway app can do it, it does. The laptop earns a job only by being physically necessary.

stays in the cloud
  • CRM on Railway, Postgres on Railway, sites on Vercel, demos on Neon.
  • Cron-shaped Claude work as scheduled routines on the Anthropic account — morning sweeps, weekly care audits, anything a clock triggers.
  • API-key Anthropic calls as the fallback path for the admin UI when no worker is alive.
  • Mail, calendar, monitors, notifications — unchanged, already cloud.
belongs on the laptop
  • On-demand Claude Code runs on the subscription, triggered from a button in the CRM rather than a clock.
  • Browser puppets that need a real, logged-in Chrome: Lighthouse, screenshots, tab snapshots, CDP prod verify.
  • Optional local inference on the GPU for high-volume, low-stakes extraction. VRAM-dependent, phase four.
  • LAN and local-file work — nightly care-plan backups onto the 3 TB, local checkouts.

The Mac mini that was pencilled in for mid-2027 is not on this path. A headless worker has no macOS dependency. If a second box ever arrives it registers as another worker on the same table.

03 — the contract

One jobs table, and nothing else crosses the line

The CRM writes a row. A worker, somewhere, claims it over the same Postgres connection the CRM already uses, does the work, and writes the result back onto the row. No inbound ports, no tunnel, no webhook into the house. Tailscale exists only so you can SSH in.

Cloud enqueues

A server action or routine inserts jobs row: kind, payload, priority, idempotency key. The UI shows it as queued.

→

Worker claims

Polls every 30–60 s with FOR UPDATE SKIP LOCKED, sets claimed_by, holds a lease with a heartbeat.

→

Result lands

Row moves to done or failed with result JSON and artefact paths. Downstream rows (tasks, proposals, notes) are written through existing actions.

db/schema.ts — sketch, names final at build time
// Every cross-boundary request is one of these. Nothing else crosses.
export const jobs = pgTable("jobs", {
  id:          uuid().defaultRandom().primaryKey(),
  kind:        text().notNull(),            // notebook.scan | puppet.lighthouse | puppet.shots | leftoff.snapshot
  payload:     jsonb().notNull().default({}),
  status:      jobStatusEnum().notNull().default("queued"), // queued | claimed | running | done | failed | cancelled
  priority:    smallint().notNull().default(2),
  runAfter:    timestamp({ withTimezone: true }),  // quiet hours, backoff
  claimedBy:   text(),                      // worker name, e.g. "ryzen-3080"
  claimedAt:   timestamp({ withTimezone: true }),
  heartbeatAt: timestamp({ withTimezone: true }),  // lease; stale → back to queued
  attempts:    smallint().notNull().default(0),
  maxAttempts: smallint().notNull().default(3),
  result:      jsonb(),
  error:       text(),
  // same replay contract as POST /api/tasks: the same pair twice returns the first row
  refKind:     text(),
  refId:       uuid(),
  requestedBy: uuid().references(() => users.id),
  createdAt:   timestamp({ withTimezone: true }).notNull().defaultNow(),
  finishedAt:  timestamp({ withTimezone: true }),
})

// Optional, for a status pill on the dashboard. The CRM still never addresses a worker.
export const workers = pgTable("workers", {
  name:       text().primaryKey(),
  lanes:      text().array().notNull().default([]),   // ["claude","puppet","gpu"]
  lastSeenAt: timestamp({ withTimezone: true }).notNull(),
  version:    text().notNull().default(""),
})

Idempotent by construction

Enqueue carries refKind/refId. Clicking Scan twice on the same notebook returns the queued row, not a twin. Same rule the tasks API already enforces.

Failure is a state, not an alert

Laptop off: rows sit queued and the UI says so. Laptop dies mid-job: heartbeat goes stale, a sweep tick requeues it. Three failures: failed, with the error on the row, and a task made through the existing triage path.

Connection hygiene

The worker opens one connection: max: 1, idle_timeout set. The Railway hobby cap has been tripped before; the worker must not be the thing that trips it again.

Three kinds to start. Each has a trigger, an executor, an output, and a budget.

05 — the worker

Two lanes on one machine

The Claude lane and the GPU lane want Linux. The puppet lane wants the Chrome you are actually logged into, which lives on the Windows side. Rather than fight WSL's browser story, the worker runs as two small services that claim from the same table by kind.

Lane A — WSL2 Ubuntu, systemd

  • Node worker under a systemd unit, Restart=always, distro set to boot with Windows.
  • Claims notebook.scan and any future claude.* kind.
  • Runs claude -p with --output-format json, --allowedTools scoped per kind, --append-system-prompt from the skill file, --max-turns capped.
  • Auth: CLAUDE_CODE_OAUTH_TOKEN from claude setup-token. One-year expiry; the expiry date goes on a task the day it is minted.
  • Phase four: Ollama with CUDA passthrough in the same lane.

Lane B — native Windows, scheduled task

  • Node worker registered as a logon-triggered task that restarts on failure.
  • Claims puppet.* and leftoff.snapshot.
  • Drives system Chrome with a persistent profile signed into the accounts the puppets need. One manual sign-in, then it stays.
  • Lighthouse CLI installed globally; artefacts written to D:\tk-artefacts\<job id>\ and served nowhere — the CRM stores paths, Tailscale fetches files.
worker/.env — the whole configuration surface
WORKER_NAME=ryzen-3080
WORKER_LANES=claude              # lane B sets: puppet,leftoff
DATABASE_URL=postgresql://...rlwy.net/railway   # public URL; the internal host does not resolve here
CLAUDE_CODE_OAUTH_TOKEN=...      # lane A only; minted 2026-11-15, expires 2027-11-15
TK_DEVICE_TOKEN=...              # for POST /api/tasks and the leftoff endpoints
POLL_SECONDS=45
QUIET_HOURS=01:00-06:00          # claude lane sleeps; puppets run through
Do not set ANTHROPIC_API_KEY, CLAUDE_CODE_USE_BEDROCK, CLAUDE_CODE_USE_VERTEX or CLAUDE_CODE_USE_FOUNDRY in lane A's environment. Any of them outranks the subscription token and silently moves the bill back to the API.

06 — the machine

Turning a gaming laptop into a server that stays up

Ryzen 9, RTX 3080 laptop, 48 GB, 3 TB. The hardware is not the risk; Windows defaults and laptop thermals are. This is the prep list, in order, before a single job runs.

Power and uptime

  • Power plan: never sleep on AC, never turn off the disk, lid close does nothing.
  • Auto sign-in after reboot so both lanes come back without a keyboard.
  • Windows Update: active hours pinned to the working day, feature updates deferred, restart notifications on.
  • Battery: leave it in as a built-in UPS if the health check passes; pull it if it is swollen or under 60 % health.
  • BIOS: power-on after AC loss, if the board offers it.

Thermals

  • Open it, clean the fans, repaste if it has never been done.
  • Stand it on its rear edge or a cooling riser so both intakes breathe.
  • Cap the GPU power limit at roughly 70 % for sustained inference. Laptop 3080s throttle hard past that and the last 30 % of watts buys little.
  • Log the temperatures for the first week of jobs before trusting an overnight batch.

Software

  • WSL2 Ubuntu 24.04 with systemd=true in wsl.conf; distro starts at logon via a scheduled task.
  • NVIDIA driver on Windows; CUDA toolkit inside WSL only if phase four goes ahead.
  • Node LTS in both lanes; Claude Code CLI in lane A; Chrome stable and Lighthouse in lane B.
  • Tailscale on Windows, SSH server enabled, key-only.

Storage on the 3 TB

  • D:\tk-artefacts\ — job outputs, pruned after 90 days by the worker.
  • D:\tk-backups\ — nightly care-plan site backups pulled over Tailscale. Answers the open “local + cloud dual redundancy” task already on the board.
  • D:\models\ — Ollama cache, phase four.
  • Local Sites checkouts stay on the Mac. The laptop is a worker, not a second dev machine.

07 — budget and limits

What it costs, and what it could quietly eat

~30 Widle drawRoughly 22 kWh a month at idle. A few dollars. Load bursts are short and rare at current job volume.
1shared usage windowThe worker spends the same 5-hour Pro/Max window you work in. A runaway scan at 14:00 is your afternoon gone.
$0new subscriptionsTailscale free tier, Ollama free, Lighthouse free. The API key stays funded as fallback, spent only when no worker is alive.

Guardrails on the Claude lane

  • Concurrency of one. The worker never runs two Claude jobs at once.
  • Extraction kinds pinned to Sonnet or Haiku via --model; Opus-class models only when a job kind explicitly asks.
  • --max-turns set per kind, never unbounded. A scan is three turns, not a conversation.
  • Quiet hours on the Claude lane so overnight routines do not drain the window you need at 09:00.
  • Token counts from the JSON result land on jobs.result, so a week of usage is one query away.

Open

before phase 0

8 or 16 GB of VRAM

Read it off nvidia-smi. Sixteen makes phase four comfortable at 14B; eight caps it at 7–8B quantised. Nothing before phase four depends on the answer.

before phase 1

Where job logs live

jobs.result alone, or also an agent_sessions row per Claude job so the ledger sees the hours. Recommendation: both, with the session summary pointing at the job id.

before phase 2

Nightly scan: routine or worker

A cloud routine can enqueue and a worker can execute, or the routine can do the whole scan itself on the account. Recommendation: routine enqueues, worker executes, so the two paths share one code path and one quality bar.

before phase 3

Artefact delivery

Screenshots and Lighthouse reports stay on the laptop disk with paths in the CRM, or get pushed to object storage so the CRM can show them inline. Recommendation: paths first, storage only if a client-facing surface needs them.

10 — done looks like

Acceptance

  • Mac closed, laptop on: Scan on a notebook page produces new actionables within five minutes, billed to the subscription, with the token count on the job row.
  • Laptop off: the same click shows queued, not an error, and falls through to the API path if you choose it.
  • Kill the worker mid-job: the row returns to queued on the next sweep tick and completes on restart. No twin rows.
  • Worker unseen for 15 minutes: the existing monitors table raises it like any other down service.
  • The setup token's expiry is a dated task on the board from the day it is minted.
  • A care-plan audit run overnight includes Lighthouse scores it gathered itself.
