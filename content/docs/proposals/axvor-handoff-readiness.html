AXVOR Handoff Readiness

AXVOR is about to be handed to a client who will edit it in Elementor without a developer. The site itself is sound — every page loads clean, the sitemap is correct, and the pages open in the builder. What is not ready is the editing experience: a marketer will find controls that look live and do nothing, and layouts that come apart when they drag a card to a new place. This is the audit and the remediation, approved and deferred to the post-launch pass.

00 — start here

Recommended actions, in order

The order matters. The first two items make controls that already exist start working, which is far cheaper than building anything new — and the second one is a set of one-line deletions with no visual consequence at all.

1

Reconcile the page specs to the live pages

So dqs build-page stops being destructive. The AXVOR changes were deliberate, so the database is canonical and the specs must come up to meet it. Provable in a loop, because the builder's element ids are deterministic.

4 sections to drop · field-level deltas on 4 pages

2

Delete the redundant real property from ~8 CSS blocks

Each of these writes both Elementor's --padding-* variable and the real padding. The variable already carries the same value, so removing the property restores a sidebar control at zero visual cost.

one-line deletions · no design change

3

Make .dqs-feature-row exemplary

Move gap and alignment onto the container's real Elementor controls and delete the CSS that overrules them. Seven live instances — the most repeated band on the site, and the one a marketer touches first.

4

Fix the widget control gaps

The hero height dropdown that cannot represent its own data, and the three editor previews that disagree with the front end.

5

Populate Elementor's global colours and fonts

A read-only mirror of brand-tokens.json, so the brand is visible in the UI without a global edit being able to repaint the site.

6

Redesign the ledger hairline maths

The one finding that cannot be fixed by specificity. Treat as its own piece of design work rather than folding it into the tidy-up.

What is ready, and what is not

The distinction that matters: nothing is disabled. There are no remove_control hooks in dqs-core or the theme, no excluded user roles, and every container control is present in the sidebar. The controls are all there — CSS just overrules them, so they look functional and do nothing.

That is the worst failure mode for a handoff. A control that is greyed out teaches the editor something. A control that moves, previews, saves and changes nothing teaches them that the site is broken and they cannot tell where.

02 — sitemap

Working, and correctly gated

The sitemap is owned entirely by tall-seo-aieo (class-tall-seo-sitemap.php), which disables WordPress core's own at line 55. /sitemap_index.xml serves a valid index pointing at page-sitemap.xml, which carries every published page with a real lastmod and an XSL stylesheet so it renders as a table in a browser. llms.txt points at it correctly.

It is inert today only because blog_public = 0 — robots.txt is Disallow: / and every page carries noindex, nofollow. That is correct for a staging domain and should stay that way until launch.

The launch switch

1

Uncheck Discourage search engines

Settings → Reading. This is the single switch that gates everything above.

2

Run wp rewrite flush

The sitemap's rewrite rules live in the plugin's activation hook, which a deploy never re-runs. Without a flush, every sitemap URL survives only on a REQUEST_URI fallback that force-sets a 200.

3

Verify on the real domain

robots.txt should lose Disallow: / and gain exactly one Sitemap: line; the noindex meta should disappear; canonicals should have moved off wpenginepowered.com.

Corrected 11 Sep 2026. An earlier draft of this section said /wp-sitemap.xml returns 404 once rewrites are flushed. Tested directly: it 301s to /sitemap_index.xml, deliberately, via a redirect in SEOEO — as does /sitemap.xml. The 404 belongs to a different thing: WordPress core's own sitemap does 404 while blog_public = 0, which is every Local and staging build. Both statements are true about different endpoints, and neither is a defect to fix.

03 — specs

Make build-page safe to run

Today a rebuild would silently re-add sections that were deliberately removed and discard edits made in the builder. The AXVOR changes have been intentional throughout, so the live pages are canonical and the specs need to be brought up to them — not the other way round.

Field-level deltas: hero video_loading: eager and an emptied stats repeater on home; a marketer's inline font-size: 23.8px span in home's The Value heading; heading copy on newsroom and contact.

Why this is provable rather than hopeful

The builder's element ids are substr(md5('dqs-bp-' . $seed), 7) — fully deterministic from a stable seed. Rebuilding an unchanged spec therefore produces byte-identical output. That turns "the spec matches the page" from an assertion into something the machine can check.

Per page: snapshot _elementor_data → fix the spec → rebuild → diff against the snapshot → repeat until the diff is empty. An empty diff means the page did not move and the spec is now canonical. Run solutions first — if the control case is not already clean, the loop itself is wrong.

04 — the editing experience

Controls that look live and do nothing

The workspace already prescribes the fix. dqs-architecture.mdc says to keep theme layout at (0,2,0), using :where() to trim weight, so it sits above Elementor's .e-con defaults and below the sidebar. :where() appears zero times across all 26 audited stylesheets. The rule was written and never applied.

Specificity is only half the story, and the smaller half. Elementor's container controls ship as custom properties — --padding-block-start, --gap, --width — consumed once by .e-con at (0,1,0). A theme rule that writes the real property beats that at any specificity at or above (0,2,0): the variable the sidebar writes is simply never read. No amount of setting it higher in the sidebar helps.

Dead controls, by how likely a marketer is to hit them

Feature rows — the entire Layout tab 7 live

dqs-page.css:222–245

Gap, align-items, align-self on both columns, justify-content on the copy column, and a 44%/56% width split that only applies at 1025px and up — so the sidebar appears to work on tablet and does nothing on desktop. This is the most repeated band on the site and the first thing anyone will try to adjust.

Icon-feature rails — head and cells both locked 5 live

dqs-page.css:1078–1086, :1147, :1158–1163

The head writes a bare padding: 0 and margin-block-end rather than the variables, so padding and bottom margin are unreachable on every rail — plus display, grid columns, align, gaps, width, and per-card padding at (0,3,0).

Section heads — eight properties

dqs-page.css:1860–1875

Layout, direction, align-items, gaps, width, text-align and margin-bottom, all as real properties. Padding works, because that half of the block correctly writes variables. Nothing else does.

Capability rows — !important on four Solutions rows

dqs-page.css:3242, :3258

Added on 11 Sep 2026 while matching the client's deck. It kills Align Self on eight columns and Padding Top/Bottom on all four rows. Ours, and ours to undo.

Stats film, newsroom bands and image-box plates

dqs-page.css:2896–2909, :3037, :3114–3166, :917–927, :1226–1233

Align-self, padding, margin and the player/figures flex split behind !important; and on every icon card and ledger cell, forced display, width and margin that kill the Image Box width and spacing controls.

Cover hero — the inverse failure 6 live

dqs-cover-hero.css:29–32

Here the sidebar does work, and that is the problem. Touching Advanced → Margin on a hero ties the full-bleed rule, Elementor loads later and wins, and the hero silently collapses into the 1200px grid.

No escape hatch

Elementor's Advanced → Custom CSS field generates at selector-scoped (0,3,0) without !important, so it cannot beat the rules above. A marketer who needs different padding on a capability row has no path at all — not through the sidebar, and not through custom CSS either.

What breaks when they rearrange things

Ledger hairlines have two sources of truth 5 bands

The builder stamps a dqs-ledger--cols-N class while the CSS keys its borders off child indices. Change Grid → Columns from 3 to 4 — the obvious move when adding a card — and the grid reflows while the hairline maths does not: stray vertical rules mid-row, missing flush left edges, a top rule cutting through the first row. Nothing in the editor hints that a class needs changing too.

This one cannot be fixed by specificity. It needs the border maths driven off the grid itself rather than child indices — a real piece of design work, not a tidy-up.

Stats and footprint rails hardcode four columns

dqs-stats.css:209, dqs-footprint.css:237

Both with :first-child-only flush edges. Adding a fifth repeater row — the most natural edit there is in a stats widget — wraps it with the wrong indent and no separating rule. The stats ledger does not wrap at all; five figures squeeze into one row and the numerals collide.

Media-text decorations read DOM position, not a flip flag 7 rows

Media-left versus media-right is which column comes first. Drag to flip a row and the photo's edge overrun pulls the wrong way while the heavy corner masks stamp on the inside edge. Four of the seven are the Solutions capability deck, which was built specifically to alternate. Insert a third widget into the row and every decoration disappears at once.

Cross-section and conditional rules

dqs-section--leads-into uses an adjacent-sibling selector across two sections, so inserting anything between them leaves a lopsided seam. The newsroom film pins mobile order by class and desktop order by DOM, so fixing one view breaks the other. And a :has() rule shrinks the gap under a section heading the moment someone deletes the deck paragraph, with no control showing why.

05 — widgets

Control gaps in the custom widgets

The hero height dropdown cannot represent its own data

The control offers 50 / 70 / 90 / 100vh. The live values are:

home 94vh solutions 60vh solutions 52vh newsroom 40vh contact 40vh our-story 50vh

Five of six heroes hold a value the dropdown has no option for. The first touch of that control silently re-heights the hero. Converting it to a slider in vh makes every existing value survive and become editable — no data migration.

Three editor previews disagree with the front end

The CTA banner's preview hardcodes its button classes, so the style dropdown changes the front end and does nothing on canvas. The footprint widget's preview drops the bundled map and shows pins floating on an empty plate. The contrast widget escapes one way in render() and the other in its preview, so markup renders bold in the editor and as literal tags on the site.

Three dead fields on the homepage

In film-split mode the builder blanks the stats widget's eyebrow, heading and description and moves the real copy into sibling widgets. Verified live: all three are empty. Fill one in and either nothing happens or you get a second heading.

A latent landmine

The builder emits a dqs-showcase widget type for which no class exists and none is registered. Nothing triggers it today; the first spec to use a showcase section would produce an invisible widget.

06 — globals

The brand is invisible in the UI

Elementor's kit has zero global colours and zero global typography, and both the colour-scheme and typography-scheme defaults are disabled. That combination is correct for a token-driven theme, but it means a marketer opening Site Settings sees nothing at all, and every "Global" colour picker in the interface has nothing to offer.

Mirror the palette from brand-tokens.json into the kit — the navy, the two blues, the text and surface tokens, and the two font stacks. A read-only mirror: the tokens stay the source of truth and the widgets keep consuming CSS variables, so the brand becomes visible in the interface without a global edit being able to repaint the site or break a contrast ratio.

07 — boundaries

Deliberately out of scope

Markup inside headings

Ten of fifty-six headings carry <strong> or a responsive line-break tag that a marketer sees as literal text in the sidebar field. Karol's call to leave them — the two-tone accent is worth the rough edit field. Goes in the handoff guide instead. The trailing space after the break tag is load-bearing.

No Style tab on custom widgets

None of the six custom widgets exposes typography, colour or spacing controls. That is the design: the theme owns the visual system. "Make this headline bigger" stays a developer ticket, and the handoff guide should say so plainly rather than leave it to be discovered.

Cross-site plugin reconciliation

Each site carries its own drifted clone of dqs-core and dqs-foundations. Reconciling now would be wasted work; it happens once in preprod across all three sites. Everything in this proposal lands in the axvor clone only.
