So a month in which nobody opens the insights page produces no archived snapshot, and the month cannot be reconstructed afterwards because the APIs have moved on.

The object is right, the table is right, the unique constraint on (site_id, period) is right. The trigger is a human remembering.

Two endpoints exist purely to be called by something that does not exist

/api/monitors/sweep has been waiting since it was written. /api/insights/gsc-scan joined it yesterday. Both are correct, both are authenticated, both do nothing until something invokes them. An earlier proposal asked who would and never got an answer; that answer is now Railway cron on the CRM, which is what this proposal builds around.

03 — the shift

Three objects, one of them new

exists — gains a schedule

A Job

Something that runs, reports in through /api/events/run, and opens a ticket when it fails. Monitors already model this and already carry their own interval. A scheduled job is a monitor that also knows what to execute, which is one field, not a subsystem.

exists — gains a writer

A Period

A frozen month: snapshot_archive plus its reports row. Unchanged in shape. What changes is that a clock closes it on the first of the month rather than a person happening to open a page in the last week of it.

new

A Digest

The short thing a person actually reads. Not a dashboard and not the archive — a handful of sentences saying what changed, what broke, and what needs a decision. Daily it is exceptions only and usually empty; weekly it is internal; monthly it is the client report, which already has a sample.

the only object here that does not exist yet

One ticker, not five cron entries

Railway can schedule a service directly, and the obvious shape is one cron entry per job. The better shape is the one this codebase already uses: a single ticker every fifteen minutes that asks each job whether it is due, exactly as monitors:sweep asks each monitor whether its sweepEveryMinutes has elapsed.

It means changing a cadence is a database update rather than a redeploy, a job that overruns cannot collide with its own next start, and there is one place to look when something did not run — which matters more than it sounds, because the failure mode of scheduled work is silence.

Five distinct jobs. The ticker runs every fifteen minutes and starts whichever of them is due, which is why the times above are intentions rather than guarantees — a job that is due at 06:00 starts by 06:15.

Daily should be silent

A daily report that arrives every day gets filtered within a fortnight. This one sends nothing unless something crosses a line: the site is down, a campaign got disapproved, spend moved sharply, clicks fell off a cliff, or a scheduled job did not report in. On a normal Tuesday it produces no output at all, and that silence is the signal.

Weekly is for you, monthly is for the client

They are different documents with different jobs. The weekly one is allowed to be blunt — a keyword died, a page slipped, a lead came in through a term you did not expect. The monthly one is the record: what was found, what was fixed, what it earned, what carries forward. The sample already shows the shape, including the part where it reports clicks falling.

06 — the clock

Railway cron, on the CRM

Your call, and the right one: one project, one place to look. A cron service in the same Railway project as the CRM, sharing its repo and its database, running one command.

tallkarol/crm — a second service in the same project
# Railway service "crm-cron" — same repo, same env, no web process
startCommand:  npm run cron:tick
cronSchedule:  "*/15 * * * *"

# scripts/cron-tick.ts — asks what is due, runs it, reports in
for (const job of dueJobs(now)) {
  await report(job, "running", runId)          // /api/events/run
  try {
    const stats = await job.run()
    await report(job, "succeeded", runId, stats)  // stands down any ticket
  } catch (err) {
    await report(job, "failed", runId, err)     // opens or escalates one
  }
}

Every job reports through the endpoint that already exists, so a failure raises a ticket without any new alerting, and monitors:sweep catches the case the endpoint structurally cannot see — a job that never starts at all. That pairing is already built and currently guards nothing.

The one thing the decision does not reach

Four of the five jobs are pure CRM work and move to Railway cleanly. The fifth is the Search Console pull into daedalus-insights/data/, and that CLI runs on your laptop against a local git repo. Railway cron on the CRM cannot call it.

This matters more than it looks. That archive is the only copy of history Google deletes at sixteen months — the fourteen months of pre-cutover baseline that made migration analysis possible at all exist nowhere else. A weekly pull that depends on you remembering is the same failure mode as the monthly report that depends on you clicking Refresh, which is the bug this whole proposal exists to fix.

Three ways out, in section 08. It is the only real decision left.

08 — before building

One decision, and two numbers

1. What happens to the archive on your laptop?

What I need: a choice between three, none of them wrong.

A — the CRM absorbs the pull. Port the Search Console archiving into tallkarol/crm and write windows to Postgres instead of files. One system, one clock, one backup. Costs a port, and daedalus-insights becomes an analysis tool over data it no longer owns.

B — insights gets deployed too. A second Railway service running the CLI on its own cron, keeping the file archive as a committed repo. Truest to the existing split, and it is a second thing to deploy and watch.

C — leave it manual, honestly. You run insights pull when you think of it. Cheapest today, and it is the failure mode this proposal is about.

My call: A. You have decided the clock lives in one spot, and an archive the clock cannot reach is not really scheduled. The pull is one API call and a write — it is far less code than keeping two deployments in step, and the sixteen months already collected import once and never need moving again.

2. What counts as an exception worth waking you for?

What I need: the lines the daily job checks against.

Site down and job-did-not-run are obvious. The rest need a number: how far clicks can fall week on week before it is worth a message, what daily ad spend is abnormal, and whether a single disapproved ad is a same-day alert or a weekly line. Set them too tight and the daily digest becomes noise and gets ignored; too loose and it never speaks and gets ignored anyway.

My call: start deliberately quiet — site down, job silent, campaign disapproved, spend more than double the daily average. Nothing about ranking or traffic, because at 130 clicks a month the week-to-week noise is larger than any signal a daily check could find.

3. Does the client see the monthly report, or do you?

What I need: whether the first of the month sends anything outward, or files it for you to send.

The reports table already models this — due then filed — and /portal/reports already exists as a client surface. So both are cheap; the question is whether a report reaches a client without you reading it first.

My call: file it as due, notify you, and let you release it. The sample report says clicks fell 16.6% — a true, useful sentence you would want to have read before the client does. Same reasoning as the claim-promotion gate in part one: the machine prepares, you publish.
